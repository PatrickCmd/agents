Part 1Introduction to Async

The Problem: Waiting Around

Consider this everyday scenario. You're making breakfast:

  1. Put bread in the toaster (takes 3 minutes)
  2. Boil water for tea (takes 4 minutes)
  3. Fry an egg (takes 5 minutes)

The synchronous approach — do each thing one after another:

Synchronous — Total: 12 minutes
START
 ├── Toast bread ............... 3 min
 ├── Boil water ................ 4 min  (toaster sitting idle)
 ├── Fry egg ................... 5 min  (kettle sitting idle)
END

The async approach — start each task, then come back when it's ready:

Async — Total: 5 minutes
START
 ├── Put bread in toaster ──────────┐
 ├── Put kettle on ─────────────────┤
 ├── Start frying egg ──────────────┤
 │                                  │
 │   ... all three happening at     │
 │       the same time ...          │
 │                                  │
 ├── Toast pops  (3 min) ──────────┤
 ├── Kettle boils (4 min) ─────────┤
 ├── Egg done    (5 min) ──────────┘
END

In programming, the things we "wait around" for are called I/O-bound operations: network requests (API calls, database queries), file reads/writes, user input. Your CPU is idle while the network does its thing. Async lets you do useful work during that idle time.

Three Ways to Do Things Concurrently in Python

Python gives you three main models for doing multiple things at once. They solve different problems and are NOT interchangeable.

1. Multiprocessing — True Parallelism

┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  Process 1   │  │  Process 2   │  │  Process 3   │
│  (own GIL)   │  │  (own GIL)   │  │  (own GIL)   │
│  CPU core 1  │  │  CPU core 2  │  │  CPU core 3  │
└──────┬───────┘  └──────┬───────┘  └──────┬───────┘
       ▼                 ▼                 ▼
   Crunching          Crunching        Crunching
   numbers            numbers          numbers
  • What it does: Spawns entirely separate Python processes, each with its own memory and GIL.
  • Best for: CPU-bound work — number crunching, image processing, ML training loops.
  • Overhead: High. Spawning a process is expensive. Sharing data between processes requires serialization.

2. Threading — Concurrent, Not Parallel (in CPython)

┌──────────────────────────────────────────────────┐
│                  One Process                      │
│                  One GIL 🔒                       │
│                                                   │
│  Thread 1        Thread 2        Thread 3         │
│  ┌────────┐     ┌────────┐     ┌────────┐        │
│  │API call│     │API call│     │API call│         │
│  │waiting…│     │waiting…│     │waiting…│         │
│  └────────┘     └────────┘     └────────┘        │
│                                                   │
│  OS schedules threads; can be interrupted          │
│  at any time (preemptive scheduling)               │
└──────────────────────────────────────────────────┘
  • What it does: Runs multiple threads within one process. Python's GIL means only one thread executes Python bytecode at a time — but threads release the GIL while waiting for I/O.
  • Best for: I/O-bound work when you need to use libraries that aren't async-aware.
  • Overhead: Medium. Threads share memory (risk of race conditions), and the OS decides when to switch.

3. Async (asyncio) — Cooperative Concurrency

┌──────────────────────────────────────────────────┐
│                  One Process                      │
│                  One Thread                       │
│                  One Event Loop 🔄                │
│                                                   │
│  Task A          Task B          Task C           │
│  ┌────────┐                                      │
│  │run code│                                      │
│  │ await… │──┐                                   │
│  └────────┘  │   ┌────────┐                      │
│              └──▶│run code│                      │
│                  │ await… │──┐                    │
│                  └────────┘  │   ┌────────┐      │
│                              └──▶│run code│      │
│  ┌────────┐                      │ await… │──┐   │
│  │resumed!│◀─────────────────────┘        │  │   │
│  └────────┘                               ▼  │   │
│                                          ...     │
│  Tasks voluntarily yield at "await" points       │
└──────────────────────────────────────────────────┘
  • What it does: Runs many tasks in a single thread using cooperative multitasking. Tasks say "I'm waiting, go do something else" via await.
  • Best for: I/O-bound work with async-compatible libraries — API calls, database queries, LLM integrations.
  • Overhead: Very low. No thread/process creation. No locks needed. No race conditions. Efficient for thousands of concurrent I/O operations.

When to Use What

Decision Guide
Is your code waiting for I/O (network, files, APIs)?
├── YES ─── Are the libraries you're using async-compatible?
│           ├── YES ──▶ Use asyncio ✅ (this tutorial!)
│           └── NO  ──▶ Use threading
│
└── NO  ─── Is it CPU-intensive? (math, images, ML training)
            ├── YES ──▶ Use multiprocessing
            └── NO  ──▶ You probably don't need concurrency

Why Async Matters for This Course

In this course, you'll frequently call LLM APIs, stream responses, make multiple API calls and combine results, and build Gradio interfaces. Each API call might take 1–10 seconds. With async, you fire them all off concurrently:

❌ Synchronous — ~15 seconds
result1 = call_openai("prompt 1")     # 5s
result2 = call_anthropic("prompt 2") # 5s
result3 = call_openai("prompt 3")     # 5s
✅ Async — ~5 seconds
r1, r2, r3 = await asyncio.gather(
    call_openai("prompt 1"),     # 5s ─┐
    call_anthropic("prompt 2"), # 5s ─┤
    call_openai("prompt 3"),     # 5s ─┘
)

Part 2The Event Loop

What Is the Event Loop?

The event loop is the engine at the heart of async Python. Think of it as a really efficient receptionist who manages a waiting room full of tasks.

The Event Loop
┌──────────────────────────────────────────────────────────┐
│                    THE EVENT LOOP                         │
│                                                          │
│   ┌─────────────┐    Ready Queue:                        │
│   │  Currently  │    ┌──────┐ ┌──────┐ ┌──────┐         │
│   │  Running:   │◀───│Task A│ │Task C│ │Task E│         │
│   │  Task A     │    └──────┘ └──────┘ └──────┘         │
│   └─────┬───────┘                                        │
│         │                                                │
│         │ hits "await"   Waiting for I/O:                │
│         ▼                ┌──────┐ ┌──────┐               │
│   Task A moves ─────────▶│Task B│ │Task D│               │
│   to waiting area        │(API) │ │(file)│               │
│                          └──┬───┘ └──────┘               │
│   Next ready task runs      │                            │
│                          API response arrives:            │
│                          Task B → Ready Queue             │
│                                                          │
│   🔄  Repeat until all tasks are done                    │
└──────────────────────────────────────────────────────────┘

Here's what the event loop does, over and over:

  1. Pick the next ready task from the queue.
  2. Run it until it hits an await.
  3. Park the task in the waiting area.
  4. Check if any waiting tasks have received their I/O results.
  5. Move completed I/O tasks back to the ready queue.
  6. Repeat from step 1.

A Concrete Timeline

Let's trace through three sequential await calls:

async def main():
    result1 = await fetch("https://api.example.com/a")  # Takes 2 seconds
    result2 = await fetch("https://api.example.com/b")  # Takes 1 second
    result3 = await fetch("https://api.example.com/c")  # Takes 3 seconds
⚠️ This is still sequential!

Each await pauses main() until the fetch completes. The event loop could run other tasks during the wait, but we only have one task here, so there's nothing else to run. Total time: 6 seconds.

Sequential awaits — no concurrency benefit
Time ──▶
0s       1s       2s       3s       4s       5s       6s
│        │        │        │        │        │        │
├── fetch A (waiting...) ──┤
│                          ├── fetch B (wait) ─┤
│                                              ├── fetch C (waiting...) ──┤
│                                                                        │
Total: 6 seconds

To get actual concurrency, you need multiple tasks running at the same time. We'll see how with asyncio.gather in Part 6. First, let's learn the basics.

The event loop can only switch between tasks at await points.
If your code runs a long computation without await, it blocks everything.
❌ Blocks the event loop
async def bad_function():
    total = 0
    for i in range(100_000_000):
        total += i  # no await — nothing else runs
    return total
✅ Yields at await points
async def good_function():
    async with aiohttp.ClientSession() as s:
        resp = await s.get(url)  # loop is free
        data = await resp.json() # and here too
        return data

Part 3Simple async def and await

Your First Coroutine

A function defined with async def is called a coroutine function. When you call it, you get a coroutine object — it doesn't run immediately.

import asyncio

# This is a coroutine function
async def greet(name: str) -> str:
    print(f"Starting to greet {name}...")
    await asyncio.sleep(1)  # Simulate a 1-second delay
    print(f"Done greeting {name}!")
    return f"Hello, {name}!"

# Calling it does NOT run it — returns a coroutine object
coro = greet("Alice")
print(type(coro))  # <class 'coroutine'>

# You must either:
# 1. "await" it from inside another async function, or
# 2. Run it with asyncio.run() from synchronous code

await — The Magic Word

await does two things:

  1. Pauses the current coroutine and gives control back to the event loop.
  2. Resumes the coroutine when the awaited thing is done, giving you its result.
async def make_breakfast():
    toast = await make_toast()       # Pause... resume with toast
    tea   = await make_tea()         # Pause... resume with tea
    egg   = await fry_egg()          # Pause... resume with egg
    return toast, tea, egg
Rule

You can only use await inside an async def function. Using it in a regular function gives a SyntaxError.

A Complete Working Example

import asyncio
import time

async def fetch_data(source: str, delay: float) -> dict:
    """Simulate fetching data from an API."""
    print(f"  📡 Starting fetch from {source}...")
    await asyncio.sleep(delay)
    print(f"  ✅ Got data from {source}!")
    return {"source": source, "data": f"Results from {source}"}

async def main():
    start = time.time()

    # These run sequentially
    result1 = await fetch_data("OpenAI", 2.0)
    result2 = await fetch_data("Anthropic", 1.5)
    result3 = await fetch_data("Google", 1.0)

    elapsed = time.time() - start
    print(f"\nAll done in {elapsed:.1f} seconds")

# From a .py file (see Part 4 for notebooks)
asyncio.run(main())

Output: Total time is ~4.5 seconds because they ran one after another. We'll make this concurrent in Part 6.

Async Functions Calling Other Async Functions

Async functions compose naturally — just await them. The async/await propagation rule: if a function needs to await something, it must itself be async def. This tends to "infect" upward — that's normal. It's called the "function coloring" problem.

The async call chain
plan_trip()              ← must be async (calls get_recommendation)
  └── get_recommendation() ← must be async (calls get_weather)
        └── get_weather()    ← must be async (uses await)
              └── asyncio.sleep() ← an awaitable

Part 4Running Async Code: Notebooks vs Modules

This is one of the trickiest parts of async Python, and the source of many confusing errors. The rules are different depending on where your code runs.

The Core Problem
Where is your code running?
│
├── In a .py module (script) ──▶ No event loop exists.
│                                  You must create one with asyncio.run()
│
└── In a .ipynb notebook ──────▶ An event loop is ALREADY RUNNING.
    (Jupyter / Cursor)             You must NOT call asyncio.run()
                                   Just use "await" directly in a cell!

Running Async in a Python Module (.py file)

# my_script.py

import asyncio

async def fetch_data() -> str:
    await asyncio.sleep(1)
    return "got data"

async def main():
    result = await fetch_data()
    print(result)

# Entry point — creates an event loop, runs main(), closes loop
if __name__ == "__main__":
    asyncio.run(main())
# Run from terminal:
uv run python my_script.py

Running Async in a Notebook (.ipynb)

Jupyter/Cursor notebooks already run an event loop behind the scenes. This means:

✅ Do this in a notebook
# Just await directly!
result = await fetch_data()
print(result)
❌ Don't do this in a notebook
asyncio.run(main())
# RuntimeError: This event loop
# is already running.

Side-by-Side: Same Logic, Two Environments

📄 .py module
import asyncio

async def fetch_data(name):
    await asyncio.sleep(1)
    return f"Data from {name}"

async def main():
    results = await asyncio.gather(
        fetch_data("API-1"),
        fetch_data("API-2"),
    )
    for r in results:
        print(r)

if __name__ == "__main__":
    asyncio.run(main())  # ← entry point
📓 .ipynb notebook
# Cell 1
import asyncio

async def fetch_data(name):
    await asyncio.sleep(1)
    return f"Data from {name}"

# Cell 2 — just await directly!
results = await asyncio.gather(
    fetch_data("API-1"),
    fetch_data("API-2"),
)
for r in results:
    print(r)

The nest_asyncio Escape Hatch

Sometimes you need to run code designed for scripts inside a notebook (e.g., a library that calls asyncio.run() internally). The nest_asyncio package patches the event loop to allow nested calls:

# Install
uv add nest_asyncio
# In a notebook cell — only if you absolutely need asyncio.run()
import nest_asyncio
nest_asyncio.apply()

asyncio.run(main())  # Now this works in a notebook
Use sparingly

nest_asyncio is a workaround, not a best practice. Prefer await directly in notebooks whenever possible.

Part 5Async with Gradio Callbacks

One of the delightful things about Gradio is that it natively supports async callback functions. Define your event handlers as async def and Gradio handles the rest.

Sync vs Async Gradio — Spot the Difference

Synchronous (what you know)
import gradio as gr

def greet(name: str) -> str:
    return f"Hello, {name}!"

demo = gr.Interface(
    fn=greet,
    inputs="text",
    outputs="text",
)
demo.launch()
✅ Async (just add async!)
import gradio as gr
import httpx

async def greet(name: str) -> str:
    async with httpx.AsyncClient() as c:
        r = await c.get(f"...?name={name}")
    return r.json()["greeting"]

demo = gr.Interface(
    fn=greet,  # Gradio auto-detects async
    inputs="text",
    outputs="text",
)
demo.launch()

That's it. No asyncio.run(), no special wrappers. Gradio detects that your function is a coroutine function and handles it automatically.

A Realistic Example: Concurrent LLM Calls

import gradio as gr
import httpx
import asyncio
import os

API_KEY = os.environ.get("OPENAI_API_KEY")

async def call_llm(client, prompt, style):
    response = await client.post(
        "https://api.openai.com/v1/chat/completions",
        headers={"Authorization": f"Bearer {API_KEY}"},
        json={
            "model": "gpt-4o-mini",
            "messages": [
                {"role": "system", "content": f"Respond in a {style} style."},
                {"role": "user", "content": prompt},
            ],
        },
        timeout=30.0,
    )
    return response.json()["choices"][0]["message"]["content"]

async def compare_responses(prompt):
    async with httpx.AsyncClient() as client:
        a, b = await asyncio.gather(
            call_llm(client, prompt, "concise and technical"),
            call_llm(client, prompt, "friendly and detailed"),
        )
    return a, b

demo = gr.Interface(
    fn=compare_responses,
    inputs=gr.Textbox(label="Your prompt"),
    outputs=[gr.Textbox(label="Concise"), gr.Textbox(label="Detailed")],
    title="LLM Response Comparator",
)
demo.launch()

Why This Works — Under the Hood

Gradio's Callback Routing
User clicks "Submit"
 │
 ├── Is callback async def?
 │   ├── YES ──▶ await callback(inputs)
 │   │          Runs on Gradio's event loop. Efficient!
 │   │
 │   └── NO  ──▶ run_in_executor(callback, inputs)
 │              Runs in a thread pool. Works, but less efficient.
 │
 └── Gradio is built on FastAPI + Starlette (async frameworks)
     so it already has an event loop running.

Streaming with Async Generators

import gradio as gr
import asyncio

async def stream_response(prompt: str):
    """Simulate streaming tokens from an LLM."""
    words = f"Here is a response to: {prompt}".split()
    partial = ""
    for word in words:
        await asyncio.sleep(0.2)
        partial += word + " "
        yield partial  # Gradio updates output with each yield

demo = gr.Interface(fn=stream_response, inputs="text", outputs="text")
demo.launch()
Key Takeaway

Sync callbacks are fine for simple logic. Async callbacks are better when you make I/O calls. Async + asyncio.gather is ideal for multiple concurrent I/O calls. You never need to worry about event loop management in Gradio.

Part 6Advanced: asyncio.gather

This is where async truly shines. asyncio.gather lets you run multiple coroutines concurrently and collect all their results.

The Basic Pattern

import asyncio

async def fetch(url: str, delay: float) -> str:
    print(f"  Fetching {url}...")
    await asyncio.sleep(delay)
    print(f"  Got {url}!")
    return f"Data from {url}"

async def main():
    # 🚀 All three run concurrently!
    results = await asyncio.gather(
        fetch("api.openai.com", 2.0),
        fetch("api.anthropic.com", 1.5),
        fetch("api.google.com", 1.0),
    )
    print(results)

All three started immediately! Total time: ~2 seconds (the slowest), not ~4.5 seconds (the sum).

Sequential vs Concurrent Timeline
Without gather (sequential):
Time ──▶  0s       1s       2s       3s       4s       5s
          ├── fetch A ──────────────┤                       2.0s
          │                         ├── fetch B ────────┤   1.5s
          │                                             ├── fetch C ───┤  1.0s
          Total: 4.5 seconds

With gather (concurrent):
Time ──▶  0s       1s       2s
          ├── fetch A ──────────────┤  2.0s
          ├── fetch B ────────┤        1.5s
          ├── fetch C ───┤             1.0s
          Total: 2.0 seconds ✅

Results Come Back in Order

asyncio.gather preserves the order of arguments, not the order of completion:

results = await asyncio.gather(
    slow_task(),    # finishes third  → results[0]
    fast_task(),    # finishes first  → results[1]
    medium_task(),  # finishes second → results[2]
)
# results[0] is ALWAYS from slow_task, regardless of finish order

Handling Errors

# Default: one failure cancels everything
try:
    results = await asyncio.gather(task_a(), task_b(), task_c())
except Exception as e:
    print(f"Something failed: {e}")

# With return_exceptions=True: failures become return values
results = await asyncio.gather(
    task_a(), task_b(), task_c(),
    return_exceptions=True,
)

# Check which results are errors:
for i, result in enumerate(results):
    if isinstance(result, Exception):
        print(f"Task {i} failed: {result}")
    else:
        print(f"Task {i} succeeded: {result}")

gather vs create_task

PatternUse WhenBehavior
asyncio.gather(a, b, c)You want all results togetherReturns when ALL tasks complete
asyncio.create_task(a)You want to start something and check laterReturns a Task handle immediately
 
async def main():
    # Start a slow background task
    slow_task = asyncio.create_task(fetch("slow-api.com", 5.0))

    # Do quick work while it runs
    quick_result = await fetch("fast-api.com", 0.5)
    print(f"Quick: {quick_result}")

    # Now wait for the slow task
    slow_result = await slow_task
    print(f"Slow: {slow_result}")

Dynamic Number of Tasks

async def process_all_urls(urls: list[str]) -> list[str]:
    async with httpx.AsyncClient() as client:
        coroutines = [client.get(url) for url in urls]
        responses = await asyncio.gather(*coroutines)
        return [r.text for r in responses]

asyncio.TaskGroup — The Modern Alternative (Python 3.11+)

async def main():
    async with asyncio.TaskGroup() as tg:
        task1 = tg.create_task(fetch("api-1.com", 1.0))
        task2 = tg.create_task(fetch("api-2.com", 2.0))
        task3 = tg.create_task(fetch("api-3.com", 1.5))

    # All tasks guaranteed done here
    print(task1.result(), task2.result(), task3.result())

Key difference: if any task in a TaskGroup raises an exception, all other tasks are cancelled, and you get an ExceptionGroup. More predictable than gather's default behavior.

Part 7Tips, Traps and Techniques

Trap 1: Forgetting to await

The single most common async bug. Without await, you get a coroutine object — not the result.

❌ Bug: Missing await
async def main():
    result = fetch_data()  # coroutine object!
    print(result)
    # <coroutine object fetch_data at 0x...>
✅ Fix: Add await
async def main():
    result = await fetch_data()  # actual value!
    print(result)
    # "Data from API"
Watch for this warning

RuntimeWarning: coroutine 'fetch_data' was never awaited — always take this seriously.

Trap 2: Blocking the Event Loop

If you run CPU-intensive or synchronous I/O code inside an async function, you block the entire event loop.

❌ Blocking calls
import time, requests

async def bad():
    time.sleep(5)            # BLOCKS!
    requests.get(url)        # BLOCKS!
    sum(range(10**8))       # BLOCKS!
✅ Async equivalents
import asyncio, httpx

async def good():
    await asyncio.sleep(5)     # yields
    await client.get(url)      # yields
    await asyncio.to_thread(   # offload
        sum, range(10**8))

Trap 3: Creating Coroutines Without Scheduling Them

❌ Created but never run
async def main():
    fetch_data("api-1")  # just created
    fetch_data("api-2")  # garbage collected!
✅ Await or gather them
async def main():
    await asyncio.gather(
        fetch_data("api-1"),
        fetch_data("api-2"),
    )

Trap 4: asyncio.run() Inside a Running Loop

❌ Crashes in a notebook
def my_function():
    result = asyncio.run(helper())
    return result

my_function()
# 💥 RuntimeError: This event loop
# is already running.
✅ Just await in notebooks
result = await helper()



# Works perfectly in a notebook cell

Trap 5: Logical Race Conditions

Async is single-threaded — no traditional data races. But you can have logical races when await separates a read from a write:

counter = 0

async def increment_with_gap():
    global counter
    value = counter                 # read
    await asyncio.sleep(0.1)         # ⚠️ other tasks can change counter here
    counter = value + 1             # write (may overwrite other changes!)

Technique: asyncio.to_thread

Run blocking sync code without freezing the event loop:

def expensive_computation(n):
    return sum(range(n))

async def main():
    result = await asyncio.to_thread(expensive_computation, 10_000_000)
    print(result)

Technique: Timeouts

async def fetch_with_timeout():
    try:
        result = await asyncio.wait_for(slow_api_call(), timeout=10.0)
        return result
    except asyncio.TimeoutError:
        print("API call timed out!")
        return None

Technique: Semaphores for Rate Limiting

When you have 1000 URLs but the API only allows 10 concurrent requests:

async def fetch_with_limit(url, client, semaphore):
    async with semaphore:  # only N tasks inside at once
        response = await client.get(url)
        return response.text

async def main():
    urls = [f"https://api.example.com/{i}" for i in range(1000)]
    semaphore = asyncio.Semaphore(10)

    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(
            *[fetch_with_limit(url, client, semaphore) for url in urls]
        )

Technique: async for and async with

# async with — resources needing async setup/teardown
async with httpx.AsyncClient() as client:
    response = await client.get(url)

# async for — iterating over async generators / streams
async def generate_numbers():
    for i in range(10):
        await asyncio.sleep(0.1)
        yield i

async for num in generate_numbers():
    print(num)

Exercise 7 Async Retry with Exponential Backoff Challenge

Write an async_retry(max_retries=3) decorator that retries a failed async function with exponential backoff (2 ** attempt seconds between retries), logs each attempt, and re-raises if all retries fail.

@async_retry(max_retries=3)
async def flaky_api_call(name: str) -> str:
    if random.random() < 0.6:
        raise ConnectionError(f"Failed to reach {name}")
    return f"Success from {name}!"
💡 Hint

Use functools.wraps. Inside the wrapper: for attempt in range(max_retries + 1) with try/except. On failure: await asyncio.sleep(2 ** attempt).

✅ Solution 
import asyncio, functools, random

def async_retry(max_retries=3):
    def decorator(func):
        @functools.wraps(func)
        async def wrapper(*args, **kwargs):
            last_exc = None
            for attempt in range(max_retries + 1):
                try:
                    return await func(*args, **kwargs)
                except Exception as e:
                    last_exc = e
                    if attempt < max_retries:
                        wait = 2 ** attempt
                        print(f"  Attempt {attempt+1} failed: {e}. Retry in {wait}s")
                        await asyncio.sleep(wait)
                    else:
                        print(f"  Attempt {attempt+1} failed. No retries left.")
            raise last_exc
        return wrapper
    return decorator

@async_retry(max_retries=3)
async def flaky_api_call(name):
    if random.random() < 0.6:
        raise ConnectionError(f"Failed: {name}")
    return f"Success from {name}!"

for i in range(3):
    try:
        print(await flaky_api_call("TestAPI"))
    except: print("Gave up")
Exercise 8 Producer-Consumer with asyncio.Queue Challenge

Build an async producer-consumer system:

  • Producer: generates 20 work items (numbered 1–20) at random intervals (0.1–0.5s)
  • 3 Consumers: each takes items from a shared asyncio.Queue, "processes" them (0.5–1.5s), prints progress
  • Graceful shutdown when all items are produced and consumed
💡 Hint

Use asyncio.Queue(). Producer puts items with await queue.put(item). Consumers get items in a loop with await queue.get(). Use None sentinel values (one per consumer) to signal shutdown.

✅ Solution 
import asyncio, random, time
start_time = time.time()

async def producer(queue, n_items, n_consumers):
    for i in range(1, n_items + 1):
        await asyncio.sleep(random.uniform(0.1, 0.5))
        print(f"  [{time.time()-start_time:5.1f}s] 📦 Produced {i}")
        await queue.put(i)
    for _ in range(n_consumers):
        await queue.put(None)  # poison pills

async def consumer(name, queue):
    while True:
        item = await queue.get()
        if item is None: break
        print(f"  [{time.time()-start_time:5.1f}s] ⚙️  {name} processing {item}")
        await asyncio.sleep(random.uniform(0.5, 1.5))
        print(f"  [{time.time()-start_time:5.1f}s] ✅ {name} done with {item}")

async def run_pipeline():
    queue = asyncio.Queue(maxsize=5)
    await asyncio.gather(
        producer(queue, 20, 3),
        consumer("Worker-A", queue),
        consumer("Worker-B", queue),
        consumer("Worker-C", queue),
    )
    print(f"\n  Done in {time.time()-start_time:.1f}s")

await run_pipeline()

Once you're comfortable with these exercises, you're ready to use async in real projects:

  • LLM API calls with httpx.AsyncClient or the openai / anthropic SDKs (AsyncOpenAI, AsyncAnthropic)
  • Gradio apps with async callbacks for responsive UIs

The Key Insight

Async isn't about making things faster — it's about not wasting time waiting. When your code is I/O-bound (which most LLM and API work is), async can dramatically improve throughput with very little additional complexity.
